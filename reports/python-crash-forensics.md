# Python+torch 退出期崩溃取证

> 本文件是公开摘要。完整取证记录含本机路径、会话标识与环境细节，仅保留在本地，不随仓库分发。

- 取证时间：2026-10-20（全程只读）
- 范围：某次批量探测脚本运行期间产生的崩溃报告

## 结论

1. **没有任何守护进程、LaunchAgent 或计划任务在"反复拉起"这些进程。**
   反复拉起它们的是一批 **DSH agent 会话**：在做图像超分方案选型时，反复用同一个解释器
   跑探测脚本。
2. **规模比预期大一个量级**：约 6 分半钟内产生 **14 份 Python 崩溃报告 + 1 份 gtimeout 崩溃报告**，
   全部同一崩溃签名。
3. 全部报告的 `responsibleProc` 都是 **DeepSeek Harness**：责任进程是 DSH 主进程，
   不是解释器自己崩。
4. gtimeout 的 SIGBUS 是**次生事件**：它是 `timeout` 命令在子进程被信号杀死后
   "重放同一信号"所致，不是独立故障。
5. **根因与脚本内容无关**：import 过 torchvision（含经间接引入）的进程，
   只要走正常 `exit()` 路径，就会在退出期崩；改用 `os._exit()` 即干净退出（现场实测）。

## 方法论

- 崩溃报告不一定都在 `~/Library/Logs/DiagnosticReports`——部分被移到废纸篓，
  而废纸篓本身受 TCC 限制，需直接列子目录读取。
- 同一崩溃签名的多份报告可用时间戳精度（0.01–0.07 秒）归属到不同会话，
  从而区分"一次故障连发多份"与"多次独立触发"。
