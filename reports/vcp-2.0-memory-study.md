# VCP 2.0 记忆系统研究：它做了什么，dsh-g-memory 能借什么

> 依据：2026-10-22 官网白皮书 V6（VCP 2.0 正式版，架构更新至 2026-10-20）、上游 `docs/ChangeLog.md`、
> `docs/RIVERMEMO_TOPOLOGY_V3.md`、上游 `b9215e9c` 源码结构，以及本机 dsh-g-memory 0.12.0 的实现。
> 本文只提炼“可迁移的机制”，不把 VCP 的营销表述当技术承诺。

## 0. 一句话

VCP 2.0 把记忆从“多个模块共管的向量检索”收口成一个 **原生数据运行时**：
SQLite 存事实、TDB 2-bit 存紧凑路由、AGS 存背景几何、Spike/RiverMemo 存本次查询的传播与拓扑证据，
再用 **多层时间尺度的压缩表示** 把“跨天/跨月”的连续性压到很低 token 成本。

dsh-g-memory 与它不在一个量级（单进程 Node 插件 vs Rust 原生数据库），但其中 **分层、双栈、结构审计、生命周期**
四类思路可以低成本借鉴。

## 1. VCP 2.0 记忆栈

| 层 | 机制 | 解决什么 |
|---|---|---|
| 事实层 | SQLite/WAL：正文、原始 FP32 向量、有序 Tag、版本、回执 | 真值、可审计、可重建 |
| 路由层 | TDB 2-bit / TDB-VEC：符号+强弱位平面、SM 筛选、图导航或扫描、原始向量精排 | 省 I/O 与大库扩展 |
| 背景层 | AGS（Anchored Greedy Gram-Schmidt）：局部残差 + 全局主题面 | 长期语义地形 |
| 查询层 | Spike 有界传播 + RiverMemo V2 双场（局部/迁移）+ 共享预算投影 + 动态虫洞 | “为什么想起它” |
| 排序层 | Topology V3：候选 Tag 曲线 vs 查询河网的相对拓扑 + Ω 泛函 + Direct Anchor | 结构证据约束排序 |
| 时间层 | 当前窗口 / OneRing / OneRingMemo / VCPTimeLine / RiverMemo / TDB 冷知识 | 分钟→天→月→年→永久 |
| 写入层 | 写 Actor + 有界队列、文件哈希差分、代际签名、双槽快照 | 稳定与可恢复 |

关键数字（白皮书）：双场投影节点预算默认 256；动态虫洞共鸣阈值默认 0.20、每节点最多 2 个动态席位；
TDB 2-bit 以 768 维为例约 1/16 原始行载荷；索引约累积 2.5% 变动才落盘。

## 2. 八个可单独拿走的机制

1. **事实与派生分离**：事实（SQLite）永远可重建索引；索引（TDB-VEC）是可丢弃的派生结构。
2. **双尺度场**：同一传输算子上求局部场（稳定解释）与迁移场（远距结构），不是两个召回器。
3. **查询河网 vs 全局图**：只保留“本次真的走过”的节点与边，区分“图上存在关系”和“本次传播经过”。
4. **Ω 可观测泛函**：用边激活量、涌现支持、正边流熵等三个分量几何平均，决定候选能否获得结构排序权限。
5. **Direct Anchor**：与结构通道正交的 hop-0 直接事实接触，避免“河网稀疏 = 没有直接答案”。
6. **动态虫洞**：用残差金字塔剥离出的深层残差，给历史弱边动态席位（而非新增边/重建图）。
7. **多时间尺度压缩**：OneRingMemo（近 3 天客观时间线，分钟级）、VCPTimeLine（每月一句话索引常驻，按语义展开）。
8. **写入稳定性**：写 Actor 单写者、有界队列、代际签名、AB 双槽、启动核对模型/维度/代际。

## 3. 与 dsh-g-memory 的对照

| 维度 | VCP 2.0 | dsh-g-memory 0.12 |
|---|---|---|
| 存储 | SQLite + Rust 原生运行时 | JSON/文件 + 单索引（本地 embedding） |
| 召回 | 图传播 + 双场 + 拓扑审计 | 向量相似 + judge/gate + policy |
| 联想 | 残差虫洞、AGS 几何 | 无（相似度 + 卡片整合） |
| 时间 | 窗口/日/月/年/永久六层 | recent tier（按天数）+ 永久 |
| 精确检索 | Rust DailyNoteAPI（正则/时间/Tag） | 无（只有语义） |
| 写入 | 差分同步 + 代际 + 快照 | chokidar 批处理 + genesis/live-index |
| 反馈 | 采纳/忽略自学习（白皮书 8.10） | judge/gate 决策打点，无在线反馈 |

**结论**：dsh-g-memory 的“被动浮现 + judge 门控”方向与 VCP 一致且更轻；差距集中在
**时间分层、精确检索、结构审计、写入代际** 四块。

## 4. 对 dsh-g-memory 的可落地借鉴（按性价比排序）

### P0：时间分层索引（低成本，收益直接）
- 现状：recent tier 按“天数”一刀切，长会话跨月时旧记忆只能靠语义碰运气。
- 做法：增加“月度一句话索引”文件（每月 1 行，总 token 极低），召回时先按当前 query 选 1-2 个月，
  再在该月内做语义检索；索引与记忆同源（从 cards/notes 生成）。
- 参考：VCPTimeLine 的“全部月份常驻 + 相关月份展开”。

### P0：双栈检索（语义 + 精确）
- 增加一个精确通道：FTS/正则/日期/标签过滤（SQLite FTS5 或内存倒排即可），
  与语义结果做 RRF 融合；用于“我上次说的那个 PR 编号/文件名/日期”类查询。
- 参考：VCP 的 Rust DailyNoteAPI 第二栈（Agent 主动核实）。

### P1：结构审计（Ω 的轻量版）
- 在现有 judge 之后加一层“结构证据”打分：候选与 query 的卡片关系（共现 tag、同会话、引用链）
  是否形成连通路径；路径稀疏或熵过低时不给额外排序权限。
- 不必实现双场，先用“图连通 + 边多样性”近似。

### P1：写入代际与快照
- live-index 已有批处理与追赶刷新；再加：每次重建写“代际签名”（模型/维度/索引版本），
  启动时核对，不匹配则重建而不是混用；索引双槽写入。
- 参考：VCP 的 AB 双槽 + 48 字节代际头。

### P2：反馈回路
- judge/gate 的采纳/忽略打点已存在；把“用户后续是否引用/纠正该记忆”作为弱标签，
  周期性调整 policy 的权重（离线评估，不在线改）。

### P2：残差驱动联想（实验性）
- 用“当前 query 向量 − 已解释实体向量”的残差，去找跨领域但强关联的卡片（虫洞近似）。
- 风险高、收益不确定，建议作为可选实验通道，不进入默认链路。

## 5. 不建议照搬
- **Rust 原生运行时**：dsh-g-memory 的定位是零依赖 Node 插件，引入原生库会破坏部署形态。
- **双场 Resolvent 求解**：数学重，且需要标签图规模；小库上收益不明显。
- **JEV 扩散模型**：依赖外部服务与配置，dsh 的 judge 已覆盖“要不要”的决策。
- **一库多业务**：VCP 把记忆/知识/日记收口是它的生态需要；dsh 保持单一职责更稳。

## 6. 升级工程观察（与本机部署相关）
- 上游 Dockerfile 基于 **Node 20**；本机 Node 26 下 `better-sqlite3@13` 编译失败，已改用 `~/.local/dsh-node22`。
- 2.0 的原生 KBM 需要 `NativeKnowledgeRuntime` 导出；上游预编译的 darwin-arm64 二进制不含该 ABI，
  必须用仓库源码重新编译 `rust-vexus-lite`。
- 旧 `VectorStore/`（usearch/better-sqlite3 时代）与新 VexusMemo 不是同一格式；升级后需重建索引，
  旧目录保留为回滚依据。
